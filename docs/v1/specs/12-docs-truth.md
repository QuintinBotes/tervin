# Spec 12 — Documentation truth pass

## Context

Tervin's stated promise is *"Tervin never claims a capability it does not have"*, and
`README.md` says the documentation is the part of the project that is most reliably true.
Right now the documentation contradicts itself in six places. For a project whose entire
positioning is honesty, that is a product defect, not a chore.

None of these is a lie in the sense that matters — they are drift. But drift in the one
artefact the project says to trust is worth a spec of its own.

## The inconsistencies, all verified

1. **Three different test counts are published.** `README.md:265-266` says 456 Rust / 80
   UI. `docs/TESTING.md` says 680 / 319 and warns that a *lower* number means a suite was
   silently skipped. `docs/HANDOFF.md:15` says 705 / 342. HANDOFF is newest.

   This one has teeth: TESTING.md tells a verifier to treat a lower count as a failure
   signal, so a stale published number turns a working suite into a false alarm — or
   worse, trains someone to ignore the check.

2. **`README.md:292` contradicts `README.md:20`.** The bottom Status section says "In
   development. No release, no published package, no stable data format" while the top
   notice says v0.1.0 is released and the cask and formula are updated.

3. **`npm` versus `pnpm`.** `README.md:256-268` and `CONTRIBUTING.md:12-17` use `npm
   install` / `npm run app`; `docs/TESTING.md` insists on `pnpm` with `--frozen-lockfile`
   because "`npm` will not reproduce the lockfile". `package.json` declares
   `packageManager: pnpm@10.32.1` and the repo ships `pnpm-lock.yaml`.

4. **Toolchain versions.** README says Rust 1.82+ / Node 20+; TESTING.md records
   verification against Rust 1.97.1 / Node 22.21.1. `Cargo.toml` says `rust-version =
   "1.82"`.

5. **README says the §3.2 completion design question is "open".** `COMPETITIVE-SPEC.md`
   §3.2 settled it — approach 3, ask the shell — and ran a spike.

6. **`PERFORMANCE.md` is missing a comparison §3.7 mandates.** §3.7 prescribes two
   actions, the first being *"publish a measured comparison in `PERFORMANCE.md` including
   the cases where Tervin loses."* It does not exist. This is the one place the docs
   *under*-claim by omission — the structural xterm.js-in-a-WebView disadvantage is
   admitted in COMPETITIVE-SPEC and unmeasured in PERFORMANCE.

## Slices

### 12.1 — One source of truth for the test counts
Generate them rather than writing them down. A script that runs the suites and emits the
counts, run in CI, with the docs carrying the generated value or no value at all.

The readership matrix already sets this precedent: a fixture generated by Rust and
asserted by both sides so neither can drift silently. Apply the same reasoning.

*Exit:* no hand-written test count survives in any document. CI fails if a published
count and the real one diverge.

### 12.2 — Reconcile the README
Fix the Status contradiction. Settle on `pnpm` throughout — it is what the lockfile and
`packageManager` say, and TESTING.md's reason is sound. Update the toolchain versions to
what is actually verified. Update the completion line to say the design is settled and
the implementation is in progress.

*Exit:* README does not contradict itself or any other document.

### 12.3 — The renderer comparison
Write the measurement §3.7 asks for: Tervin against Ghostty (and one of kitty or
Alacritty) on the cases that matter — large output throughput, input-to-paint latency,
memory at a large scrollback. **Include the cases where Tervin loses**, which is the
explicit instruction, and it will lose some.

`PERFORMANCE.md` already models how to do this well: it publishes the single-character
fuzzy query at 2.87ms per 20,000 files, extrapolates it to ~29ms at the 200,000 cap,
calls it "a perceptible hitch", and says the trade is not being made silently. Same
register here.

*Exit:* `PERFORMANCE.md` carries a renderer comparison with method, machine, and the
losses named.

### 12.4 — Fold the roadmap back in
This roadmap and its specs live in the scratchpad by choice. When the work lands, the
*outcomes* belong in the repository: `COMPETITIVE-SPEC.md` §1's "Not present, and worth
saying" list shrinks, §3's items get marked done with their exit criteria met, and
`HANDOFF.md` is rewritten for whoever comes next.

Do not leave a stale roadmap in the repo. Update the documents that already exist.

*Exit:* §1's baseline and §3's status reflect the code. HANDOFF describes the present.

### 12.5 — A v1.0 release-readiness checklist
`docs/MANUAL-TEST.md` §11 already covers "before distributing": install from a real
artifact on a machine that never ran Tervin, and *"Every install route in the README
actually works, or is not in the README."*

Extend it for 1.0: the npm publish route (`HANDOFF.md` #5 — blocked on 2FA, needs a
manual `npm login` from a real TTY, then trusted publishing for
`QuintinBotes/tervin/release.yml` and delete `NPM_TOKEN`), the Linux artifact from spec
10.4, and a stated position on schema stability, since `README.md` currently warns the
SQLite format is a moving target and a 1.0 should either stop moving it or keep saying so.

*Exit:* a checklist that, when green, means the release can go out.
